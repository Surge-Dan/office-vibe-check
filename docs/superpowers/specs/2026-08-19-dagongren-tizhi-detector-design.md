# 《打工人体质检测器》产品设计文档

版本：v0.1
日期：2026-08-19
状态：已确认，进入实现前评审

## 1. 产品结论

本产品是一款运行在小红书小程序/小工具环境中的轻量互动测试：用户完成 7 道工作场景选择题，生成一张具有传播感的“打工人体质档案卡”，支持保存、分享和重新测试。

第一版不接 AI、不接登录、不接后端、不采集身份信息。题目、评分规则、体质文案和分享卡全部本地化，保证导入小红书官方开发者工具后即可运行，降低审核、部署和运行风险。

产品成功标准不是“测评很专业”，而是用户产生三个反应：

1. 题目像真实发生过的职场瞬间。
2. 结果文案像在描述自己。
3. 结果卡值得发给同事或朋友。

## 2. 产品定位

### 2.1 目标用户

- 18～35 岁职场人；
- 初入职场、互联网、传媒、运营、产品、设计等办公室人群；
- 喜欢测试、职场梗和轻量互动内容的小红书用户。

产品不定位为职业测评、心理诊断或职业规划工具。结果页必须明确“仅供娱乐”，不对用户做严肃人格判断。

### 2.2 核心用户价值

- 快速表达自己的工作状态；
- 用共同的职场黑话获得共鸣；
- 生成适合小红书传播的视觉化结果。

### 2.3 MVP 范围

必须包含：

- 首页介绍；
- 7 道单选题；
- 进度展示、返回修改和重新测试；
- 本地计分与结果生成；
- 8 种体质结果；
- 结果详情页；
- 1080×1080 分享卡；
- 小红书分享入口；
- 本地保存最近一次结果。

明确不做：

- 用户登录、手机号、头像和昵称采集；
- 在线 AI 文案生成；
- 用户评论、排行榜和社交关系；
- 后台管理系统；
- 外部数据库、第三方 UI 框架和 CDN 依赖。

## 3. 用户流程

```text
进入小工具
  -> 首页：你的工位，究竟是什么体质？
  -> 点击“开始建档”
  -> 完成 7 道场景题
  -> 生成体质结果
  -> 查看体质解释和关键词
  -> 生成结果卡
  -> 保存 / 分享 / 再测一次
```

单次目标时长：45～75 秒。

## 4. 页面和功能说明

### 4.1 首页

页面内容：

- 产品标题：你的工位，究竟是什么体质？
- 副标题：做 7 道题，看看你在职场里靠什么活下来。
- 档案编号、状态标签等装饰信息；
- 主按钮：开始建档；
- 次要入口：查看上次结果。

推荐首屏文案：

> 不是职业测评。只是想知道，你每天到底是怎么活下来的。

首页只承担“理解产品”和“开始测试”两个动作，不放教程、注册和复杂说明。

### 4.2 选择题页

每页只展示一道题，包含：

- 顶部进度：`03 / 07`；
- 场景题目；
- 4 个单选项；
- 进度条；
- 上一题和下一题。

交互规则：

- 点击选项后立即选中；
- 已选选项可更换；
- 未选择时不能进入下一题；
- 支持返回修改；
- 返回修改后保留后续答案；
- 中途退出不强制保存，再次进入默认重新开始；
- 刷新后不得出现上一轮测试的脏状态。

### 4.3 结果页

结果页是产品的核心传播页面，包含：

1. 体质名称；
2. 一句概括性判断；
3. 3 个关键词；
4. 工作状态描述；
5. 典型职场反应；
6. 一句原创梗文案；
7. 生成分享卡、分享和再测按钮。

示例：

> 你是：低调卷王体
>
> 表面：问题不大，按计划来。  
> 内心：这个项目不能输。
>
> 关键词：自我驱动 / 不动声色 / 结果导向
>
> 你不是喜欢加班。你只是接受不了事情没有收口。

结果内容控制在一屏半以内，避免变成长篇职业鸡汤。

## 5. 体质库

第一版设置 8 种体质。数据结构需要支持后续扩展，但首发不超过 8 种，避免结果内容变薄、题目区分度下降。

| ID | 体质名称 | 核心状态 | 关键词 |
|---|---|---|---|
| fish-hermit | 摸鱼隐士体 | 工作不是人生，但要摸得专业 | 摸鱼、划水、带薪清醒 |
| low-key-roll | 低调卷王体 | 不喊口号，但事情一定要做成 | 结果导向、暗中发力、收口 |
| cake-immune | 画饼免疫体 | 听得懂承诺背后的真实含义 | 画饼、清醒、看行动 |
| blame-magnet | 背锅吸铁石体 | 工作越做越多，责任越背越稳 | 背锅、兜底、边界感 |
| minimum-master | 糊弄学宗师体 | 先交付，再决定要不要精致 | 最小可行、先上线、差不多 |
| class-flavor | 班味浓度超标体 | 人已经下班，灵魂还在会议室 | 班味、内耗、疲惫 |
| reverse-roll | 反向内卷体 | 不比加班，只和问题较劲 | 边界、效率、拒绝无效竞争 |
| meeting-escape | 会议逃生专家体 | 能用一句话解决，绝不扩展成会议 | 对齐、同步、闭环 |

每个体质必须包含：

- `id`；
- 体质名称；
- 一句话定义；
- 3 个关键词；
- 主要表现；
- 典型工作场景；
- 5 组以上结果文案；
- 分享卡标题和副标题；
- 推荐颜色。

## 6. 黑话和梗素材研究方案

### 6.1 当前候选语义簇

公开检索显示，职场内容中反复出现的语义包括：

- 身份：打工人、社畜、牛马、螺丝钉、力工；
- 工作方式：摸鱼、划水、内卷、躺平、摆烂、糊弄学；
- 管理话术：画大饼、向上管理、赋能、对齐、拉通、闭环、落地、沉淀、复盘；
- 工作关系：背锅、甩锅、兜底、抢功、协同；
- 工作状态：班味、精神内耗、破防、卷不动了、早日退休。

“画大饼”“向上管理”等词具有明确的职场话术语义；“摸鱼”“打工人”“内卷”等词拥有更广泛的中文互联网传播基础。[新浪职场黑话案例](https://cj.sina.com.cn/articles/view/5952915705/162d248f906702nx2c?froms=ggmp)、[牛客网职场黑话整理](https://www.nowcoder.com/discuss/736231594461081600)、[中文网络语言研究](https://www.tandfonline.com/doi/pdf/10.1080/23311983.2025.2549407)

B站公开职场内容中也持续出现“摸鱼工位”“卷不动了”“早日退休”“996”“打工人”等表达。[摸鱼工位内容](https://www.bilibili.com/video/BV1Kx421y73A/)、[打工人和 996 内容](https://www.bilibili.com/video/BV19o4y117wg/)

### 6.2 素材库字段

建立内容研究表：

| 字段 | 说明 |
|---|---|
| term | 黑话或梗 |
| sourcePlatform | 小红书、微博、抖音、B站等 |
| sourceUrl | 原始链接 |
| collectedAt | 采集日期 |
| scene | 会议、加班、周报、汇报等 |
| emotion | 自嘲、疲惫、清醒、愤怒等 |
| typeIds | 可对应的体质 |
| risk | 低风险、需改写、不使用 |
| rewrittenCopy | 产品最终使用文案 |

### 6.3 采集和改写规则

- 先收集 80～120 个候选词，再筛选为 40～60 个正式素材；
- 每个素材记录来源平台、链接和采集日期；
- 只借鉴语义，不复制用户评论或创作者的大段原文；
- 不使用地域、性别、学历、职业歧视和明显脏话；
- “社畜”“牛马”等词只作为轻度自嘲标签，不作为人格结论；
- 每个体质至少保留 5 组不同文案，避免重复；
- 后续按季度复查一次素材，替换明显过时的词。

本轮检索受公开网页可访问性限制，没有读取平台登录态内容；因此上述内容是候选素材池和研究框架，正式上线前仍需补充小红书、微博、抖音和B站的人工样本，并保留可追溯来源。

## 7. 题目设计

### 7.1 数量

固定 7 道题：

- 6 道区分工作行为；
- 1 道作为平分时决胜题；
- 每题 4 个选项；
- 单次完成预计 45～75 秒。

### 7.2 题目维度

| 维度 | 观察内容 |
|---|---|
| 截止时间 | 如何处理临时任务 |
| 加班请求 | 如何回应“辛苦一下” |
| 会议场景 | 对同步、对齐和废话的态度 |
| 领导画饼 | 对未来承诺的反应 |
| 责任边界 | 如何处理甩锅和兜底 |
| 交付策略 | 完美、效率和先上线之间的选择 |
| 下班状态 | 工作对生活的侵入程度 |

### 7.3 题目示例

**题目：下班前，领导突然说“这个今天能不能先出一个版本？”**

- A. 先确认最小交付范围，今晚把能交的交了；
- B. 直接留下来，先把完整版本做出来；
- C. 问清楚是不是真的今天要，不急就明天再说；
- D. 拉上相关同事一起确认，避免最后只有自己负责。

**题目：领导说“以后有机会给你更大的舞台”，你的第一反应是：**

- A. 记下来，等具体安排；
- B. 先把手里的事情做出成绩；
- C. 这句话听过，先看有没有实际动作；
- D. 立刻问清楚机会、时间和评价标准。

题目不应直接出现“我喜欢摸鱼”“我喜欢加班”这类标签化选项。四个选项都必须看起来合理，避免用户一眼猜出所谓“正确答案”。

### 7.4 题目验收

内部测试 20～30 人，重点观察：

- 是否出现大量无法选择的题目；
- 是否有选项被所有人选择；
- 是否存在明显的正确答案；
- 结果是否与用户自我认知大致一致；
- 是否有题目被认为过度负面或冒犯。

## 8. 结果算法

采用本地确定性加权计分，不接在线大模型。

```text
用户选择选项
  -> 累加 8 种体质分数
  -> 取最高分
  -> 同分时使用第 7 题决胜
  -> 读取体质内容
  -> 渲染结果页和分享卡
```

规则：

- 每道题最多影响 2～3 种体质；
- 不能由单道题直接决定结果；
- 结果文案使用“更接近”，不使用“你就是”；
- 结果页增加“仅供娱乐，不代表真实职业能力或人格判断”。

## 9. UI 设计方向

视觉主题：**职场档案局**。

视觉关键词：编辑部感、档案标签、黑白底色、少量荧光色、大字号中文、细线框、编号系统、适度留白。

推荐配色：

- 墨黑：`#171717`；
- 暖白：`#F4F0E8`；
- 辅助灰：`#A9A49B`；
- 荧光黄绿：`#D7F36B`；
- 低饱和橙红：`#E7795B`。

推荐视觉细节：

- 首页使用 `CASE 001`、`WORKPLACE SPECIMEN` 等档案编号；
- 题目页使用“现场记录 03 / 07”；
- 结果页做成“体质鉴定单”；
- 分享卡使用方形构图；
- 使用 CSS 线条、编号和排版制造设计感。

明确避免：

- 紫蓝渐变；
- 玻璃拟态；
- 机器人头像和 AI 星星；
- 大面积发光；
- 模板化圆角卡片堆叠；
- 过度使用 emoji。

## 10. 小红书小程序技术交付

### 10.1 交付形态

交付物必须是完整的原生小红书小程序工程，而不是普通 HTML 页面、React 页面或单个代码文件。

建议工程边界：

```text
project/
├─ app.json
├─ app.js
├─ app 样式文件（后缀以官方模板为准）
├─ pages/
│  ├─ index/
│  ├─ quiz/
│  └─ result/
├─ components/
│  ├─ question-card/
│  ├─ progress-bar/
│  └─ result-card/
├─ data/
│  ├─ questions.js
│  └─ types.js
├─ utils/
│  ├─ scoring.js
│  ├─ share-card.js
│  └─ storage.js
└─ assets/
   ├─ icons/
   └─ textures/
```

实际文件后缀和项目配置以小红书官方开发者工具当前原生模板为准。开发时必须从官方模板创建项目，不直接套用微信小程序或普通 H5 工程。

小红书官方平台提供开发者工具、框架、组件和 API，并要求经过入驻、类目与备案、开发、审核和发布流程。[小红书小程序开放平台](https://miniapp.xiaohongshu.com/)

### 10.2 技术原则

- 所有题目、体质和算法本地化；
- 不依赖后端、CDN 或第三方服务；
- 图片、纹理和图标尽量本地化；
- 不申请用户授权；
- 不采集用户身份信息；
- 断网时仍可完成测试和查看结果；
- 代码导入官方开发者工具后即可预览。

### 10.3 分享实现

第一版支持：

- 右上角分享；
- 页面内“生成分享卡”；
- 自定义分享标题；
- 自定义分享图片；
- 分享后重新打开并查看结果。

小红书页面文档提供 `onShareAppMessage`、`onShareTimeline` 和 `imageUrl` 等分享能力；分享图优先生成 1:1 本地图片，减少平台适配问题。[页面与分享接口文档](https://miniapp.xiaohongshu.com/doc/DC686827)

### 10.4 发布流程

研发和测试按照以下流程执行：

```text
本地开发
  -> 官方开发者工具预览
  -> 上传开发版本
  -> 设置体验版
  -> 真机测试
  -> 提交审核
  -> 审核通过后发布
```

小红书官方发布文档明确区分开发版本、体验版本、审核中版本和线上版本，支持预览、上传、提交审核和发布。[小程序协同工作和发布](https://miniapp.xiaohongshu.com/doc/DC980658)

## 11. 数据与隐私

MVP 只在本地保存：

```text
lastResultType
lastTestTime
```

不保存姓名、手机号、头像、小红书账号、工作单位、职业和完整答案。

后续如需埋点，可预留以下事件：

```text
page_view_home
click_start
quiz_start
quiz_complete
result_view
click_generate_card
click_share
click_restart
```

第一版不为了数据而强行接入后台，优先通过平台基础数据和小范围人工测试验证产品价值。

## 12. 指标与验收

### 12.1 观察指标

| 指标 | MVP 验证目标 |
|---|---:|
| 首页到开始测试转化率 | ≥ 60% |
| 开始到完成测试转化率 | ≥ 70% |
| 单次完成时长 | 45～75 秒 |
| 结果页停留时间 | ≥ 15 秒 |
| 结果卡生成率 | ≥ 25% |
| 分享点击率 | ≥ 15% |
| 重新测试率 | ≥ 10% |

最重要的定性指标是：用户是否愿意把结果卡发给朋友，并说“这个测得有点准”。

### 12.2 功能验收

- 首页可正常进入测试；
- 固定 7 道题，每题必须选择后才能继续；
- 支持返回修改；
- 刷新不会出现脏状态；
- 所有答案都能得到稳定结果；
- 同分时结果稳定；
- 结果与体质内容匹配；
- 分享卡可以生成；
- 无需登录和授权即可完成全部流程；
- 无外部域名和第三方服务依赖。

### 12.3 视觉验收

- 首屏不出现 AI 模板感；
- 题目阅读压力低；
- 结果页有明确记忆点；
- 分享卡缩小后仍能看清体质名称；
- 黑色背景、细线、编号和强调色保持统一；
- 无外部图片时也能正常显示。

## 13. 实施顺序

1. 内容研究：收集 80～120 个候选词，筛选出 40～60 个正式素材；
2. 体质设计：完成 8 种体质和每种至少 5 组文案；
3. 题目验证：完成 7 道题、评分映射和 20～30 人内测；
4. UI 设计：完成首页、题目页、结果页和分享卡；
5. 原生开发：按官方小红书模板实现完整工程；
6. 真机验收：重点检查分享、断网、刷新、返回和不同屏幕尺寸；
7. 上传审核：预览、上传、体验版、审核和发布。

## 14. 设计自检结论

- 范围聚焦在一个完整 MVP，没有引入登录、后台和 AI 等非必要系统；
- 题目数量、结果数量和内容资产规模相互匹配；
- 算法、页面和分享卡均采用本地确定性方案；
- 小红书适配边界与产品功能边界一致；
- “充分收集黑话”被定义为可追溯的内容研究流程，而不是无来源地堆砌网络流行语；
- 正式实现前，需要补齐多平台人工样本并进行题目内测。
